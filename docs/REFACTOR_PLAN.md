# Refactor Plan: Reducing Complexity and Improving Traceability

The goal of this refactor is to make ownership explicit, state transitions
visible in types, and individual components easy to reason about in isolation.
The guiding principles are:

- **Make impossible states unrepresentable** — encode state in types, not in
  status fields + manual counters
- **Single owner** — each piece of data has exactly one place it lives
- **RAII for side effects** — use `Drop` to enforce cleanup rather than
  manually tracking it across multiple code paths

---

## Area 1: Downloads

### Problem

Downloads today have split identity across multiple locations:

1. `PendingDownload` — lives in `ClientInner.pending_downloads` before connect,
   then moves to `ConnectedWorker.pending`
2. `Download` — lives in `ConnectedWorker.downloads`, keyed by a token that
   **changes mid-flight** via `UpdateDownloadTokens`
3. `DownloadHandle` — held by the user, connected via channel

A download can stall or never start at multiple invisible handoff points. There
is no single place to look to understand where a download is.

Additionally, `active_downloads` is manually incremented and decremented across
three separate code paths — this has already caused bugs.

### 1a. `DownloadSlot` RAII guard (small, high value)

Replace the manual `active_downloads` counter with a RAII guard:

```rust
struct DownloadSlot(Arc<AtomicU32>);

impl Drop for DownloadSlot {
    fn drop(&mut self) {
        self.0.fetch_sub(1, Relaxed);
    }
}
```

`ActiveDownload` holds a `DownloadSlot`. When the download completes, is
cancelled, or fails, the slot is freed automatically — no matter which code
path exits. It becomes **impossible** to forget to decrement the counter.

### 1b. Stable `DownloadId` + separate wire token (medium)

The `UpdateDownloadTokens` dance exists because we assign one token but the
peer assigns a different one mid-flight. Fix this by separating concerns:

```rust
struct DownloadId(u64);  // user-facing, stable, generated by us, never changes
struct WireToken(u32);   // peer-assigned, temporary, used only for wire protocol
```

The registry maps `WireToken → DownloadId` as a secondary index. `DownloadId`
becomes the stable key for everything user-visible. `UpdateDownloadTokens`
becomes a simple secondary-index update with no structural move.

### 1c. Download state machine in types (medium)

Encode the download lifecycle in the type system rather than a status field:

```rust
struct QueuedDownload {
    id:     DownloadId,
    meta:   DownloadMeta,   // filename, username, size, dir
    notify: StatusSender,
}

struct ActiveDownload {
    id:     DownloadId,
    meta:   DownloadMeta,
    notify: StatusSender,
    cancel: Arc<AtomicBool>,
    slot:   DownloadSlot,   // RAII — slot freed on drop
}

struct DoneDownload {
    id:     DownloadId,
    result: DownloadResult,
}
```

Transitions between states are explicit method calls, not field mutations.

### 1d. `DownloadRegistry` — single owner (medium)

Consolidate all download state into one struct owned exclusively by the worker:

```rust
struct DownloadRegistry {
    queued:    VecDeque<QueuedDownload>,
    active:    HashMap<DownloadId, ActiveDownload>,
    wire_index: HashMap<WireToken, DownloadId>,  // secondary index only
    done:      Vec<DoneDownload>,
    slots:     Arc<AtomicU32>,
    max:       Option<u32>,
}

impl DownloadRegistry {
    fn enqueue(&mut self, download: QueuedDownload) { ... }
    fn activate(&mut self, id: DownloadId) -> Option<ActiveDownload> { ... }
    fn complete(&mut self, id: DownloadId, result: DownloadResult) { ... }
    fn remap_token(&mut self, old: WireToken, new: WireToken) { ... }
    fn find_by_wire_token(&self, token: WireToken) -> Option<&ActiveDownload> { ... }
}
```

To trace any download: check `queued` → `active` → `done` in order. The full
lifecycle is visible in one struct.

## Area 2: Searches

### Problem

- `searches` is keyed by query **string**, but search results arrive keyed by
  **token** — causing an O(n) linear scan on every result
- Two searches with the same query string clobber each other
  (`searches.insert(key, ...)` replaces the previous entry)
- Completed searches are never removed — the map grows indefinitely

### Fix: `SearchRegistry` keyed by token (small)

```rust
struct SearchRegistry {
    searches: HashMap<SearchToken, Search>,
    // optional: index by query string for lookup from Client::search()
    by_query: HashMap<String, SearchToken>,
}
```

`SearchResult` dispatch becomes an O(1) lookup. Two searches for the same
query get independent entries. Cleanup is a simple `remove(token)` when the
search times out.

## Area 3: The `ClientOperation` enum

### Problem

`ClientOperation` is a single enum that mixes five conceptually different
things:

- Server events (`LoginSucceeded`, `ServerDisconnected`, `NewPeer`)
- Peer events (`DownloadFromPeer`, `UpdateDownloadTokens`, `UploadFailed`)
- Download lifecycle (`RequestDownload`, `DownloadCompleted`,
  `PierceFirewallPreTokenFailed`)
- Control messages (`SetServerSender`, `PierceFireWall`, `ConnectToPeer`)
- Query operations (`QueryDownloads`, `QuerySearchResults`, etc.)

Any component can send any variant to the worker with no type-level constraint.
A new contributor has no way to know which variants come from which source.

### Fix: Split into scoped enums

```rust
enum ServerEvent   { LoginSucceeded, ServerDisconnected, NewPeer(NewPeer), ... }
enum PeerEvent     { DownloadFromPeer(...), UpdateDownloadTokens(...), UploadFailed(...), ... }
enum DownloadOp    { Request(PendingDownload), Completed(DownloadId, Result<...>), SlotFreed }
enum WorkerQuery   { Downloads(oneshot::Sender<...>), SearchResults(...), ... }

enum WorkerMessage {
    Server(ServerEvent),
    Peer(PeerEvent),
    Download(DownloadOp),
    Query(WorkerQuery),
}
```

The worker's match becomes nested but each arm has a clear origin. Sources can
be constrained by type — a peer actor can only send `PeerEvent`, not
accidentally send `SetServerSender`.

## Area 4: `ServerActor` read/write model

### Problem

- `process_read()` uses `try_read()` poll driven by the 100 ms tick — up to
  100 ms latency on inbound messages
- `send_message()` uses `try_write()` — silently drops messages when the socket
  send buffer is full (`WouldBlock`)
- `initiate_connection()` calls `std::net::TcpStream::connect()` — a blocking
  call on an async runtime thread

### Fix: Proper async I/O

- Replace `std::net::TcpStream::connect()` with
  `tokio::net::TcpStream::connect().await`
- Replace the tick-driven `try_read()` loop with `stream.readable().await` in
  the actor's event loop (requires the `Actor` trait to support an async select
  branch, or moving `ServerActor` off the generic actor framework)
- Add a write buffer (`VecDeque<Bytes>`) drained on `writable().await` rather
  than dropping on `WouldBlock`

This likely requires extending or partially bypassing the `Actor` trait for
`ServerActor`, since the current `tick()` / `handle()` design is synchronous.

## Area 5: `state_monitor` indirection

### Problem

`state_monitor` is a dedicated task whose only job is to relay two events
(`ServerDisconnected`, `LoginSucceeded`) to `ClientInner.state`. The
`WorkerEvent` enum and extra task exist solely to avoid giving the worker a
reference to `ClientInner`.

### Fix: Give the worker a direct state handle

```rust
struct WorkerState(Arc<Mutex<ClientState>>);  // newtype, only exposes set_connected / set_disconnected

// worker holds:
state: WorkerState,
```

The worker calls `self.state.set_connected()` directly. One fewer task, one
fewer channel, the `WorkerEvent` enum is deleted.

## Suggested order of implementation

| Step | Change | Value | Effort |
|---|---|---|---|
| 1 | Key `searches` by `SearchToken` | Fixes O(n) scan + clobber bug | Small |
| 2 | `DownloadSlot` RAII guard | Eliminates counter bug class | Small |
| 3 | Stable `DownloadId` + wire token separation | Eliminates `UpdateDownloadTokens` | Medium |
| 4 | `DownloadRegistry` struct | Single owner, easy to trace | Medium |
| 5 | Remove `state_monitor`, give worker direct state | Reduces indirection | Small |
| 6 | Split `ClientOperation` into scoped enums | Clearer message origins | Medium |
| 7 | Async read/write in `ServerActor` | Fixes latency + message loss | Large |
| 8 | Download state machine in types | Full type-safe lifecycle | Large |
